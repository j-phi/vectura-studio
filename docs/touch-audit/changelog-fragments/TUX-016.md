# TUX-016 toolbar footer and drag handles are touch-safe

## CHANGELOG bullet
- Touch: the toolbar footer (pin, home, rotate, pop-out) no longer renders on a coarse pointer, and the 14 px toolbar grip and 16 px context-bar grip are now 44 px finger targets with `touch-action: none`. A one-finger drag on either grip moves its bar 1:1 (it moved 16 of 80 px before, then the browser cancelled the gesture). A cancelled context-bar drag no longer leaves listeners that drag the bar on a later unrelated touch. In `mobile-layout` the static rail has no grip and no footer for any pointer type. A persisted toolbar lock is ignored on a coarse pointer (the desktop preference is kept), and a floating-bar drag is clamped on release so the bar cannot get lost.

## Ownership and hand-offs
- TUX-013 requirement 4 (footer hidden) is satisfied by TUX-016. TUX-013 must not write its own footer-hide CSS. The TUX-016 block is the last word: `body.mobile-layout #tool-bar .toolbar-drag-handle, .toolbar-footer { display: none }` and `@media (pointer: coarse) { #tool-bar .toolbar-footer { display: none } }`.
- Deviation from the brief: the brief said `body.touch-ui` does not exist. TUX-006 landed before this lane merged. The CSS and JS still key on `(pointer: coarse)`, which is the signal that sets `touch-ui` (primary pointer). This stays correct on touch-screen laptops.
- Interface request for lane S2 / TUX-045: remove `.toolbar-drag-handle` from the `ui-touch.js` mouse-bridge selector (about line 69). The handle uses only pointer listeners, so the synthetic mouse events are harmless but useless.
- Interface request for TUX-018: replace the local begin/end lifecycle in `context-bar.js` `bindHandleDrag` with `bindPointerDrag` when it lands (TODO left in code).
- §5.3 edges to add to docs/touch-ux-requirements.md: TUX-006 -> TUX-016 (layout class and touch-ui). TUX-001 -> TUX-016 (iPhP numbers: before TUX-001 Chromium iPhP innerWidth was 544, not 402; the iPhP test asserts visibility only, never widths).
- Optional follow-up: a View-menu "Reset toolbar position" entry (calls `ui.resetToolbarPosition`). Not added: `header.js` belongs to another lane. Factory reset stays in App.clearSavedPreferences.
