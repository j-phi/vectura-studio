## The DEFAULT_LAW fix (U1, not in the plan's literal text)

`ladder` is the shipped default and deliberately **not** a member of `SCENE3D_TONE_LAWS.IDS` (confirmed: `IDS.indexOf('ladder') === -1`). C-01's survivor IS `ladder`, so the moment U1 added its `COLLAPSE` row, the build script's own §2.1 integrity throws (`ALIASES[x].into ∈ PICKER_IDS`, every option's `law ∈ IDS`) would have rejected the very first row — `PICKER_IDS` is derived from `IDS`, and `'ladder'` can never be a member of either. This is specific to C-01 (the only cluster whose survivor is the shipped default, not a roster id) — U2-U5 never needed it, confirmed by their own clean `node scripts/build-tone-laws.js` runs.

### A genuine, newly-discovered gap from this step (not previously known, not in any unit's report.json)

The Fill Style row correctly resolved and displayed **"Ladder (default)"** (proving `SCENE_FILL_STYLES.resolve('fineLadder')` → `'ladder'` works live, not just in jsdom). But the **Rung detail sub-control showed "Coarse — 4 rungs," not "Fine rungs."** I verified this is a **display-only bug, not a rendering regression**: `Params.resolveToneLaw(obj.params.style.params)` on the live layer (queried directly in the browser console) still correctly returns `'fineLadder'` (rule 2 — a raw alias id passes through unchanged), so the actual geometry on canvas is the real fine-ladder pattern, byte-identical to what it always was. The bug is that `fillStyleControls`'s sub-control renders from `o.paramsBag` — the **raw, unmigrated** `style.params` object (`{fillCurves:true, toneLaw:'fineLadder'}`, no `rungMode` key) — because `_applyVecturaPayload`'s load path never runs `normalizeStyle`'s migration shim on it (confirmed live: `obj.params.style.params` is still `{toneLaw:'fineLadder'}` after reload, not `{toneLaw:'ladder', rungMode:'fine'}`). With no `rungMode` key present, the sub-control falls back to its own descriptor default ("coarse") for display purposes only.

This is the **same class** of gap `STILL-OPEN.md`'s already-queued **W-10d-2** item describes generally (`_composeSceneGroup` feeding `algo.generate()` without ever calling `normalizeParams`/`sanitizeSceneParams`, so a live in-session or freshly-loaded styleTable is never migrated) — but it is a **new, specific instance** of it for the collapse's own aliases, not previously documented anywhere. It does not corrupt the render (verified) and does not affect this chain's byte-identity oracle (which is about the render). It is a genuine UX inconsistency: a user opening an old file with a folded law sees the WRONG sub-control value until they touch the picker once (which would write the full resolved bag going forward). Flagging as **W-10d-3** (a sibling of the existing W-10d-2 item) for whoever picks up that queued item — same root cause, same fix shape (gate `normalizeStyle`/the collapse shim into the load or live-compose path), likely fixable in the SAME follow-up unit as W-10d-2 rather than a new one.
